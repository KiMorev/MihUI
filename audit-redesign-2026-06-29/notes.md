## Вывод

Опасение про перегруженность подтверждается. Проблема не только в плотности карточек, а в том, что один длинный экран одновременно решает несколько разных задач:

- загрузить/сохранить конфиг;
- редактировать подписки;
- редактировать группы;
- объяснить маршрутизацию;
- показать текущие ноды Mihomo;
- настроить фильтры по нодам;
- показать рекомендации;
- показать diff;
- показать итоговый YAML.

Из-за этого пользователь теряет контекст: после скролла непонятно, в каком режиме он находится и какое действие сейчас главное.

## Что видно по референсам

zashboard и MetaCubeXD выносят подключение к backend в отдельный setup-сценарий. Yacd разделяет рабочие режимы на понятные области: Overview, Proxies, Rules, Conns, Config, Logs. Их аккуратность возникает из разделения задач, а не только из цветов или скруглений.

## Предлагаемая структура

1. **Обзор**
   - состояние конфига;
   - число подписок, групп, нод;
   - рекомендации;
   - ошибки проверки;
   - основные действия: открыть, сохранить, проверить.

2. **Подписки**
   - список provider-ов;
   - карточка редактирования выбранной подписки;
   - фильтр, исключения, типы, интервалы;
   - обновление/статусы подписок.

3. **Маршрутизация**
   - сценарии из rules;
   - список групп;
   - редактор выбранной группы;
   - связи `proxies` и `use`.

4. **Ноды**
   - live-список Mihomo;
   - поиск и фильтры;
   - действия по названию/протоколу для filter и exclude;
   - отображение подписки, группы, протокола, статуса.

5. **Проверка и вывод**
   - что изменится;
   - рекомендации по подключению;
   - итоговый YAML;
   - проверить в ядре, копировать, скачать.

6. **UI / сервис**
   - ссылки на существующие UI;
   - обновление MihUI;
   - настройки локального сервиса, если появятся.

## План переделки

1. Ввести верхнюю навигацию по разделам и состояние активного раздела.
2. Разнести существующие блоки по разделам без изменения бизнес-логики.
3. Сделать контекстные action-кнопки внутри каждого раздела, а не одну общую кучку в topbar.
4. Пересобрать layout разделов: каждая страница должна иметь один главный рабочий объект.
5. Отдельно пройти mobile: разделы должны идти как страницы, а не как длинная лента всех функций.
6. После структурной переделки пройти визуальный слой: плотность, отступы, заголовки, empty states.

## Риск

Это лучше делать не одним гигантским коммитом. Первый безопасный шаг — разнести блоки по вкладкам/разделам без изменения логики и форматов данных. После этого уже можно аккуратно улучшать каждый раздел.
